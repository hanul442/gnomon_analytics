# 실제 결제 설계

2026-10-12 기준(v3.19.11). [ROADMAP.md](ROADMAP.md) 3단계 "실제 결제 연결 설계"의 결과물이에요. **설계만 하고 구현은 하지 않아요.** 구현은 한서님이 개인사업자 등록을 마친 뒤에 시작해요. 그 전까지 화면은 MOCK(알파 사이트에서는 "알파 기간에는 결제를 받지 않아요" 안내, G-216)이고, 권한은 `plans.ts`의 `FEATURES` 표(G-215)가 정해요.

결정의 근거는 계속 [DESIGN.md](DESIGN.md)의 G-번호에 남겨요. 아래 "정할 것"은 구현을 시작할 때 한서님이 고르는 항목이에요.

## 1. 결제를 열기 전에 끝낼 일

순서대로예요. 앞의 일이 끝나야 뒤의 일을 할 수 있어요.

1. **개인사업자 등록**: 업종은 정보통신업(응용 소프트웨어 개발 및 공급 또는 데이터베이스·온라인 정보 제공). 간이과세와 일반과세 중 무엇이 맞는지 세무사에게 확인해요. 간이과세면 세금계산서 발행에 제약이 있어요.
2. **통신판매업 신고**: 온라인으로 돈을 받으려면 필요해요. PG 계약 때 구매안전서비스 확인증을 받아 신고해요.
3. **유사투자자문업 신고 여부 확인**: DESIGN.md §6(432행)대로, 유료로 종목 의견을 주면 자본시장법상 신고 대상일 수 있어요. 그노몬은 매수·매도 권유를 하지 않지만, 유료화 전에 전문가 확인을 받아요. 신고 대상이면 교육 이수와 신고를 마친 뒤 결제를 열어요.
4. **PG 계약**: 아래 2장의 PG와 계약하고 정기결제(빌링) 사용 심사를 받아요. 심사에는 사업자등록증, 통신판매업 신고증, 이용약관·환불정책이 걸린 사이트 주소가 필요해요.
5. **약관 고치기**: `terms.html`에 유료 서비스 조항, 환불정책(4장), 자동 갱신 고지를 넣어요. 사이트 맨 아래에 사업자 정보(상호, 대표자, 사업자등록번호, 통신판매업 신고번호, 주소, 연락처)를 표시해요.

## 2. PG 고르기

| 후보 | 장점 | 단점 |
|---|---|---|
| **토스페이먼츠 (추천)** | 개인사업자도 바로 계약, 빌링키 정기결제 API가 단순, 결제창이 휴대폰에서 깔끔, 테스트 키로 계약 전에 개발 가능 | 정기결제 스케줄은 우리가 돌려야 함(PG가 매달 알아서 긁지 않음) |
| 포트원(아임포트) | 여러 PG를 한 API로, 나중에 PG를 바꾸기 쉬움 | 한 단계가 더 끼어 수수료·장애 지점이 늘어남. 지금 규모에서는 이점이 작음 |
| 앱 마켓 인앱결제 | 앱 설치 사용자에게 편함 | 그노몬은 웹(PWA)이라 해당 없음. 수수료가 큼 |

**기본안: 토스페이먼츠 빌링(자동결제) + 일반결제(크레딧 충전).** 계약 전에도 테스트 키로 끝까지 만들어 볼 수 있어서, 사업자 등록과 개발을 나란히 진행할 수 있어요. API 이름과 주소는 구현 시점의 토스페이먼츠 문서를 다시 확인해요.

## 3. 무엇을 파나

`plans.ts`에 이미 있는 값을 그대로 써요. 가격은 부가세 포함이에요.

| 상품 | 가격 | 결제 방식 | 주는 것 |
|---|---|---|---|
| 플러스 | 14,900원/월 | 정기결제 | `users.plan = 'plus'`, 매달 100크레딧 |
| 프로 | 39,000원/월 | 정기결제 | `plan = 'pro'`, 매달 400크레딧, 충전 +10% |
| 맥스 | 99,000원/월 | 정기결제 | `plan = 'max'`, 매달 1,150크레딧, 충전 +20% |
| 100·300·1,000크레딧 | 9,900·27,900·84,900원 | 한 번 결제 | 충전 크레딧(1년), 플러스부터 |

- 권한은 지금처럼 `users.plan` 하나만 봐요. `FEATURES`·`allows()`·`needText()`는 바꾸지 않아요. 결제가 하는 일은 **`users.plan`을 바꾸고 원장(`ledger`)에 크레딧을 넣는 것**뿐이에요.
- 알파(`plan = 'alpha'`, 프로로 침)는 결제를 연 뒤에도 정해진 날까지 유지해요(7장).
- 연간 요금제, 쿠폰, 무료 체험은 처음에는 넣지 않아요. 넣을 때는 상품 행만 늘어나고 흐름은 같아요.

## 4. 환불과 취소 원칙

전자상거래법의 청약철회(7일)를 따르되, 디지털 콘텐츠는 **써 버린 만큼은 돌려받을 수 없다는 것을 결제 전에 고지**해야 제한할 수 있어요. 결제 화면과 약관에 같은 문장을 넣어요.

- **구독 해지**: 언제든 해지할 수 있고, 지금 기간 끝까지 그 요금제를 써요. 다음 달부터 안 긁혀요. 해지는 환불이 아니에요.
- **구독 환불**: 결제 후 7일 안이고 그 달 포함 크레딧을 하나도 안 썼으면 전액 환불하고 바로 무료로 내려요. 크레딧을 썼거나 7일이 지났으면 해지만 돼요.
- **충전 크레딧 환불**: 결제 후 7일 안이고 하나도 안 썼으면 전액. 일부 썼으면 남은 크레딧 비율만큼 환불(보너스 크레딧은 빼고 계산). 7일이 지난 뒤에도 남은 충전 크레딧은 1년 안에 요청하면 비율만큼 돌려줘요(정할 것 ①).
- **서비스 장애**: 우리 잘못으로 리포트·질문이 실패하면 지금처럼 크레딧을 자동으로 되돌려요(원장의 refund 행). 돈 환불이 아니라 크레딧 환불이에요.

## 5. 데이터 구조

지금 원장은 "잔액 = 행의 합"이고 `(user_id, ref)`가 유일해서, 같은 결제를 두 번 넣어도 한 번만 들어가요. 결제는 이 성질을 그대로 이용해요.

새 표(마이그레이션 `00xx_payments.sql`):

```sql
-- 한 사람에 하나. 지금 구독 상태의 원본.
CREATE TABLE subscriptions (
  user_id TEXT PRIMARY KEY,
  plan TEXT NOT NULL,              -- plus | pro | max
  status TEXT NOT NULL,            -- active | canceling | past_due | ended
  billing_key_enc TEXT,            -- PG 빌링키, 암호화해서 저장(아래)
  customer_key TEXT NOT NULL,      -- PG에 보내는 고객 식별자(이메일 아님, 무작위)
  card_label TEXT,                 -- '신한 1234' 처럼 화면 표시용
  period_start TEXT NOT NULL,      -- 지금 기간 (KST 날짜)
  period_end TEXT NOT NULL,
  next_charge_at TEXT,             -- 다음 결제 시도 시각, 해지하면 NULL
  fail_count INTEGER NOT NULL DEFAULT 0,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

-- 돈이 오간 기록. 우리 쪽 주문번호가 기준.
CREATE TABLE payments (
  order_id TEXT PRIMARY KEY,       -- 우리가 만든 주문번호, PG에 그대로 보냄
  user_id TEXT NOT NULL,
  item TEXT NOT NULL,              -- plus | pro | max | c100 | c300 | c1000
  kind TEXT NOT NULL,              -- subscribe | renew | topup
  amount INTEGER NOT NULL,         -- 원
  status TEXT NOT NULL,            -- pending | paid | failed | canceled | partial_canceled
  payment_key TEXT,                -- PG 결제 키
  canceled_amount INTEGER NOT NULL DEFAULT 0,
  receipt_url TEXT,
  created_at TEXT NOT NULL,
  paid_at TEXT
);
CREATE INDEX payments_user ON payments (user_id, created_at);

-- 받은 웹훅 원문. 같은 이벤트를 두 번 처리하지 않게.
CREATE TABLE payment_events (
  id TEXT PRIMARY KEY,             -- PG 이벤트 id 또는 payment_key + status
  order_id TEXT,
  body TEXT NOT NULL,
  received_at TEXT NOT NULL,
  handled_at TEXT
);
```

원장 쪽:

- 크레딧을 줄 때 `ref`를 결제에 묶어요. 구독 포함 크레딧은 `sub:{user}:{period_start}`, 충전은 `pay:{order_id}`, 환불 회수는 `refund:{order_id}`. 같은 웹훅이 두 번 와도 한 번만 들어가요.
- **크레딧 유효기간이 필요해요.** 지금 원장은 만료가 없어요. 약관 초안대로 "포함 크레딧은 이월 안 됨, 충전 크레딧은 1년"을 지키려면 `ledger`에 `expires_at` 열을 더하고, 쓸 때는 먼저 끝나는 크레딧부터 써요(지금 MOCK의 체험 크레딧과 같은 규칙, `plans.ts` spend). 기간이 바뀌면 남은 포함 크레딧만큼 `expire` 행을 넣어 0으로 맞춰요. 잔액 계산은 "합"을 유지해서 기존 코드가 그대로 돌아요.
- 빌링키는 카드 정보가 아니지만 그것만 있으면 결제가 되니 비밀로 다뤄요. Worker 비밀값(`PAYMENT_KEY_SECRET`)으로 AES-GCM 암호화해서 저장하고, 화면에는 `card_label`만 보여요.

## 6. 흐름

### 6.1 구독 시작

1. 요금제 화면에서 "프로 시작하기" → `checkout.html?item=pro`. 로그인 안 했으면 로그인부터.
2. 화면이 `POST /billing/start {item}`을 불러요. 서버는 `customer_key`를 만들고(없으면) 결제창에 넘길 값을 돌려줘요.
3. 토스 결제창에서 카드를 등록하면 `success` 주소로 `authKey`가 돌아와요.
4. 화면이 `POST /billing/confirm {authKey}` → 서버가 PG에 빌링키 발급을 요청하고, 바로 첫 달 결제를 승인해요(`payments`에 `subscribe` 행, `order_id`는 서버가 만듦).
5. 승인되면 한 트랜잭션(D1 batch)으로: `subscriptions` 행 만들기, `users.plan` 바꾸기, 포함 크레딧 넣기(`ref = sub:…`), `payments.status = paid`.
6. 화면은 `/me`를 다시 불러 요금제와 크레딧을 그려요.

결제 승인 응답을 놓쳐도(창 닫힘, 연결 끊김) 웹훅이 같은 일을 다시 하고, `ref` 덕분에 두 번 들어가지 않아요.

### 6.2 매달 갱신

토스 빌링은 PG가 알아서 긁지 않아요. 지금 Worker에 있는 cron(`*/10 * * * *`)에 "갱신할 구독 찾기"를 붙여요.

- `next_charge_at <= now`이고 `status = active`인 구독을 몇 개씩 꺼내 결제를 승인해요(`kind = renew`, `order_id = renew:{user}:{period_start}` 처럼 기간마다 정해진 값이라 cron이 겹쳐도 한 번만 승인돼요).
- 성공: 기간을 한 달 밀고, 지난 포함 크레딧을 만료시키고, 새 포함 크레딧을 넣어요.
- 실패(잔액 부족, 카드 만료): `past_due`로 바꾸고 `fail_count`를 올려 1일, 3일 뒤 다시 시도해요. 그동안 요금제는 유지하고 화면 위에 "결제가 안 됐어요, 카드를 바꿔 주세요" 띠와 메일·푸시를 보내요. 세 번 다 실패하면 `ended`, `users.plan = 'free'`(정할 것 ②).

### 6.3 요금제 바꾸기

- **올리기**(플러스 → 프로): 바로 바꾸고, 남은 기간만큼 차액을 일할로 지금 결제해요. 포함 크레딧은 새 요금제 기준으로 차이만큼 더 넣어요. 다음 결제일은 그대로.
- **내리기**(프로 → 플러스): 지금 기간 끝까지 프로, 다음 결제부터 플러스. `subscriptions`에 `next_plan`을 둬요.

처음 구현에서는 올리기만 하고, 내리기는 "해지 후 기간 끝나면 다시 가입"으로 안내해도 돼요(정할 것 ③).

### 6.4 해지와 환불

- **해지**: `POST /billing/cancel` → `status = canceling`, `next_charge_at = NULL`. 기간이 끝나는 cron에서 `ended`, `plan = 'free'`, 남은 포함 크레딧 만료.
- **환불**: 4장 조건을 서버가 계산해요(크레딧을 썼는지는 원장에서 그 기간의 spend 행으로 봐요). 사용자가 직접 누르는 버튼은 7일 안 전액 환불만 두고, 나머지는 운영 화면에서 운영자가 처리해요. PG 취소 API로 전액·부분 취소 → `payments.status`, 원장에 회수 행(`refund:{order_id}`), 구독이면 `plan = 'free'`.

### 6.5 크레딧 충전

일반결제예요. `POST /billing/topup {item}` → 결제창 → `POST /billing/topup/confirm {paymentKey, orderId, amount}`. 서버는 **금액을 화면 값이 아니라 상품표로 다시 계산해서** PG 금액과 맞는지 보고 승인해요. 승인되면 `ref = pay:{order_id}`로 크레딧과 요금제 보너스(프로 +10%, 맥스 +20%)를 넣어요.

### 6.6 웹훅

`POST /billing/webhook`. 웹훅 본문은 믿지 않고 **PG 조회 API로 그 결제를 다시 읽어서** 상태를 정해요(위조 방지). 처리 순서: `payment_events`에 원문 저장(이미 있으면 끝) → PG에서 결제 조회 → `payments` 상태가 다르면 6.1·6.4와 같은 함수로 맞추기 → `handled_at` 기록. 화면 쪽 confirm과 웹훅이 같은 함수를 부르니, 어느 쪽이 먼저 와도 결과가 같아요.

## 7. 알파에서 넘어가기

- 결제를 여는 날을 정하고(정할 것 ④), 그 날까지 알파 계정은 그대로 프로 권한과 매달 400크레딧이에요.
- 여는 날부터 새 가입은 무료로 시작해요. 기존 알파 테스터는 여는 날 + 30일까지 알파를 유지하고, 그 뒤 무료로 내려요. 알파 테스터에게는 첫 달 할인 쿠폰을 줄 수 있어요(정할 것 ⑤).
- 알파 때 받은 크레딧은 남겨 두되 충전 크레딧과 같이 1년 유효로 바꿔요.
- 운영자가 손으로 주는 크레딧(크레딧 요청 승인, 운영자 조정)은 결제를 연 뒤에도 그대로 둬요.

## 8. 화면

- 요금제 화면: "MOCK"·"알파 기간" 안내를 지우고, 사업자 정보와 환불정책 링크를 아래에 둬요. 지금 요금제, 다음 결제일, 카드(`card_label`)를 맨 위 카드에 보여요.
- 결제 화면(`checkout.html`): 주문 내용, 자동 갱신 고지("매달 ○일에 ○원이 결제돼요, 언제든 해지"), 환불 제한 고지, 동의 체크, 결제 버튼. 결제 수단 라디오는 지우고 PG 결제창이 맡아요.
- 내 계정: 구독 관리(카드 바꾸기, 해지, 해지 취소), 결제 내역과 영수증 링크.
- 운영 화면: 결제·환불 탭(최근 결제, 실패한 갱신, 환불 처리 버튼).
